Usage: four steps, one loop.

BareSpec splits a feature into a contract and a checklist. A feature moves through four slash commands, and each one writes a file the next one reads.

context.md holds the project background every skill reads. spec.yaml is the requirement contract for one feature, and plan.md is its ordered task checklist. The agent implements the plan task by task and records what changed.

Every step reads and writes plain files in your repo, so you can stop after any command and pick up later.

Every command is described in the command reference.

Status follows the work.

The status field in spec.yaml tells you, and the next skill, where a feature stands.

  1. draft

    set by /spec-create

    Spec contract written, no plan yet.

  2. ready

    set by /spec-plan

    Plan generated, ready to implement.

  3. in-progress

    set by /spec-implement

    Implementation started.

  4. done

    set by /spec-implement

    Implementation completed.

A spec whose requires list names specs that are not done cannot be implemented yet. When a spec finishes, BareSpec reports which dependent specs are now unblocked.

Add your own steps.

Hooks are plain-text instructions the agent follows before or after a skill. There are no scripts to maintain.

Hooks live in barespec/barespec.config.yml, which /init-config creates. Each of the six steps takes a pre and a post list: context, spec, plan, implement, review and visualize.

  1. pre hookse.g. check git status
  2. the skillany BareSpec step
  3. post hookse.g. run lint and tests

The config file is optional. Without it, every skill runs without hooks.

What lands in your repo.

Everything lives in one barespec/ folder, so it is easy to review, commit or ignore.

  • context.md is shared by every skill.
  • spec.yaml holds the requirements for one feature, plan.md its tasks.
  • visual.html exists only if you ran /spec-visualize. Committing it is up to you.

Command reference

Run the skills as slash commands in any compatible AI coding agent. Each step builds on the file the previous one wrote. The examples below are illustrative.

1.0 Capture the project

/init-context

Creates or updates barespec/context.md, the file every other skill reads for background: product, architecture, tech stack and non-functional requirements.

The skill inspects your codebase first, then interviews you in rounds to close the remaining gaps. Run it again after a feature changes the architecture or stack.

2.0 Write the feature spec

/spec-create <feature>

Defines the requirement contract in barespec/specs/<name>/spec.yaml, with status draft. Requirements are grouped into components, and each one gets an ID such as user-auth.LOGIN.1-1 that the plan refers to later.

If the spec already exists you can update it or start a new one. Updating resets it to draft so the plan can be regenerated.

3.0 Plan the work

/spec-plan <spec-name>

Breaks the spec into ordered, testable tasks in plan.md. Every task carries the requirement IDs it satisfies and a check for when it is done.

You confirm the breakdown before it is written, and the spec moves to ready. If a plan already exists you choose between regenerating it and appending tasks.

4.0 Build it

/spec-implement <spec-name>

Works through plan.md task by task, checking each one off, and moves the spec from in-progress to done. Run it again to resume from the first unchecked task.

It stops if the spec is still draft or if a spec listed in requires is not done. On completion it updates context.md and records development notes.

5.0 Review the diff

/spec-code-review [fixed-point] [spec-name]

Optional and read-only. Reviews the diff between HEAD and a fixed point (a commit, branch or tag) along two independent axes, coding standards and spec, each run by its own sub-agent. With no fixed point it reviews your uncommitted changes.

It reports findings and never edits code, checks off tasks or changes a spec’s status. The spec comes from the argument, the branch name or a recently updated spec; with none, give a one-line description of the intent instead.

6.0 See the spec

/spec-visualize [spec-name]

Optional and read-only. Renders a spec and its plan as visual.html: status, version and dates, a requirement tree with a coverage badge on every ID, a traceability matrix, task states, and warnings for inconsistencies.

The page is self-contained, works offline and follows your system theme. Click an ID to highlight it in every view. A spec without a plan still renders, with a “No plan yet” banner, and each run overwrites the file.

7.0 Customize the workflow

/init-config

Optional. Creates or updates barespec/barespec.config.yml, the file where you write custom instructions to run before or after each BareSpec step. If the file exists it shows your current hooks and asks whether to update them or reset to the default template.

It then asks about every hook slot in one go and writes only the events that have an instruction. What hooks are and which steps accept them is covered in Hooks.

barespec-guide is a background skill, not a command. Agents load it automatically when a conversation mentions BareSpec.
